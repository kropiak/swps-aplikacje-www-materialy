Część 1

Gałęzie i konflikty

Jedno ustawienie na start


git config --global pull.rebase false

„Przy git pull łącz zmiany zwykłym scaleniem.”
Bez tego git potrafi przerwać pull komunikatem divergent branches.

Czym jest gałąź?

Osobna linia rozwoju: eksperymentuj bez ryzyka

merge: scal, gdy działa · porzuć, gdy nie

Pierwsza gałąź


git switch -c plan-funkcji      # nowa gałąź
# dopisz w README sekcję "Planowane funkcje"
git commit -am "Dodaj listę planowanych funkcji"
git switch main                 # sekcja znika?! 😮
git merge plan-funkcji          # Fast-forward
git log --oneline
git branch -d plan-funkcji

Konflikt = ta sama linia, dwie wersje

nowy-tytul
# Konsultacje: rezerwacja wizyt
main
# Konsultacje psychologiczne

<<<<<<< HEAD
# Konsultacje psychologiczne
=======
# Konsultacje: rezerwacja wizyt
>>>>>>> nowy-tytul

Git nie zgaduje, tylko pyta Ciebie. Konflikt to po prostu tekst w pliku.

Rozwiązanie konfliktu

  1. Edytuj plik: usuń znaczniki <<< === >>>, zostaw właściwą treść
  2. git add README.md („rozwiązane”)
  3. git commit -m "Scal gałąź nowy-tytul"
  4. git log --oneline --graph 🌳
😱 Panika? git merge --abort cofa do stanu sprzed scalania

Pull request

„Przejrzyj moje zmiany z gałęzi X i scal je z main.”

  1. VS Code: nowa gałąź licznik-specjalistow → zmiana → commit → Publish Branch
  2. GitHub: Compare & pull request → opis → Create
  3. Files changed: przegląd kodu, komentarze
  4. Merge → Delete branch
  5. VS Code: main → Sync

Konflikt z GitHubem

☁️ GitHub:
- przypomnienia e-mail o wizycie
💻 lokalnie (bez pull!):
- panel administratora

Sync → konflikt → Accept Both Changes / Merge Editor
